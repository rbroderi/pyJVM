# Plan: `_sqlite3` for pyJVM (phase N6a of `native_modules_plan.md`; written by a planning agent, 2026-11-16)

Planning only: nothing here is implemented, and no build, pytest or conformance run was made for it. Measurements were taken on `C:\Python313` (3.13.17), `C:\Python314` (3.14.10) and `C:\Python315` (3.15.2) with one-off scripts, and from CPython's C sources read with `git show` (HEAD = the pinned 3.15 commit `5b28ebd109`). Everything marked **unverified** was not measured.

## 1. Goal and scope
`import sqlite3` works on Windows and Linux x86-64 on the 3.13, 3.14 and 3.15 lanes, with CPython's `Lib/sqlite3` running unmodified on a Java `_sqlite3` that binds the SQLite C library through FFM. That also unblocks `dbm.sqlite3`, `sqlite3.dump`, `sqlite3.__main__` and (3.15) `sqlite3._completer`: 5 modules on 3.13, 6 on 3.15 in `STDLIB_STATUS.md:49, 83`.
Out of scope: virtual tables and other parts of the SQLite C API that CPython does not expose; shared-cache mode (`enable_shared_cache` was removed from CPython in 3.12, so it is absent on every lane).
No dependency on N0-N3: SQLite does its own file I/O. Per the decisions of 2026-11-16 this module goes first, before the R2-01 loader, so it carries its own small library lookup (section 4).

## 4. The native library: vendored SQLite, system library as fallback
Policy (decision 5 of 2026-11-16): SQLite is a large, security-sensitive component, so it is neither re-implemented nor taken from whatever the host happens to have; pyJVM vendors it. The binding (Java, section 5) is the in-house part.

**Vendored:** the SQLite amalgamation, two files only (`sqlite3.c`, `sqlite3.h`; no shell, no Tcl, no extensions outside the amalgamation), one pinned release for all lanes (proposed: 3.53.4, what `C:\Python315` ships and the newest measured here), under `third_party/sqlite/` with a `VERSION` file holding the release and the SHA3-256 of the download. Built per platform into a private library `pyjvm-sqlite3-<version>.dll` / `libpyjvm-sqlite3-<version>.so`, with CPython's Windows options as measured through `pragma compile_options` (`ENABLE_FTS3`, `ENABLE_FTS4`, `ENABLE_FTS5`, `ENABLE_RTREE`, `ENABLE_MATH_FUNCTIONS`, `ENABLE_PERCENTILE`, `OMIT_AUTOINIT`, `THREADSAFE=1`, `TEMP_STORE=1`; load-extension support left in, since every lane has `enable_load_extension`).
- "Shaded" for a C library means: a private file name; only the `sqlite3_*` API exported (`-fvisibility=hidden` plus `SQLITE_API` on Linux, an export list on Windows); `-Wl,-Bsymbolic` on Linux so that a system `libsqlite3.so.0` loaded into the same process by someone else (a ctypes user, a JNI library) can neither capture our internal calls nor be captured by them. FFM looks symbols up per library (`SymbolLookup.libraryLookup(path, Arena.global())`), so nothing is taken from the global namespace.
- Licence: SQLite is in the public domain (no notice or attribution is required, and it is compatible with GPL-3.0-or-later and the linking exception). Add an entry to `THIRD_PARTY_LICENSES` anyway (the policy asks for a list of everything vendored): the release, the hash, the public-domain dedication text and the build options.
- Build: a committed `tools/vendor_sqlite.py` compiles the amalgamation with the host C compiler (`cl`, `cc`, or `zig cc`, which the extension plan already uses for cross builds) into the work directory. The compiled library is not committed (standing rule: no compiled artefacts in the repository) and, once R2-01 exists, ships in the runtime jar under `META-INF/pyjvm/native/<os>-<arch>/` through its extraction cache. Whether this machine has a usable C compiler was **not verified** (Rust 1.91.1 is installed, which on Windows normally means the MSVC tools are too).

**Lookup order at `import _sqlite3`** (class init of the FFM layer, lazy so that nothing loads before the import):
1. `PYJVM_SQLITE3`: an explicit library path (used by the gates, see section 9).
2. The vendored build: beside the runtime (`<runtime>/native/<os>-<arch>/`), later the R2-01 cache.
3. System fallback: `libsqlite3.so.0` on Linux; on Windows `winsqlite3.dll` from System32.
4. Otherwise `ImportError` naming what was looked for (CPython built without SQLite lacks the module in the same way).
Version floor for a system library: 3.15.2 (`Modules/_sqlite/module.c:37`, `#if SQLITE_VERSION_NUMBER < 3015002`), checked with `sqlite3_libversion_number()`; below it, `ImportError`. Optional symbols are probed, not assumed (`sqlite3_keyword_count` needs 3.24, `sqlite3_create_window_function` 3.25, `sqlite3_serialize` a build option, `sqlite3_load_extension` a build option); a missing one makes the Python method absent or raise `NotSupportedError` exactly as CPython's `#ifdef`s do.

Why the system library is only a fallback (measured on this machine): `winsqlite3.dll` reports 3.53.4 and exports all 95 functions checked, but it is built with `OMIT_LOCALTIME` and without `ENABLE_MATH_FUNCTIONS`, and with `MAX_TRIGGER_DEPTH=100` where CPython's build has 1000. So `select sin(0)` and the `'localtime'` modifier, which work on every CPython lane, would fail; its version also changes with Windows updates. On Linux the distribution's version varies (Ubuntu 22.04 is believed to ship 3.37.2: **unverified**), and uv's CPython builds link their own SQLite statically, so the reference and pyJVM would differ there too. spike S5 of `native_modules_plan.md` (winsqlite3 from Java) becomes a check of the fallback only.

## 5. FFM binding design
New files in `runtime/pyjvm315/runtime/` (both OSes; no `Posix*`/`Windows*` split is needed beyond the library lookup):
- `Sqlite3Native.java` (~550): lookup (section 4), one `MethodHandle` per C function used, about 95: open/close (`sqlite3_open_v2`, `sqlite3_close_v2`), prepare/step/reset/finalize, `bind_*`, `column_*`, error accessors, `busy_timeout`, `changes64`/`total_changes64` (fall back to the 32-bit ones below 3.37), `last_insert_rowid`, `get_autocommit`, `txn_state`, `interrupt`, `complete`, `create_function_v2`, `create_window_function`, `create_collation_v2`, `set_authorizer`, `progress_handler`, `trace_v2`, `result_*`, `value_*`, `aggregate_context`, `user_data`, `backup_*`, `blob_*`, `serialize`/`deserialize`, `limit`, `db_config`, `load_extension`, `stmt_readonly`, `stmt_busy`, `expanded_sql`, `keyword_*`, `malloc64`/`free`. No errno or `GetLastError` capture: SQLite reports through return codes. `sqlite3_db_config` is variadic in C: declare it with `Linker.Option.firstVariadicArg(2)`. `sqlite3_initialize()` once (the vendored build has `OMIT_AUTOINIT`).
- `Sqlite3Module.java` (~450): module object, constants as a data table (not a giant method: methodsize rule), exception classes, `adapters`/`converters`, `adapt`, `register_*`, `complete_statement`, `enable_callback_tracebacks`, lane gates.
- `Sqlite3Connection.java` (~800), `Sqlite3Cursor.java` (~550), `Sqlite3Statement.java` (~350: binding, column fetch, the statement cache), `Sqlite3Callbacks.java` (~400), `Sqlite3Row.java` + `Sqlite3Blob.java` (~300).

Calls and data:
- Text in: `String` -> UTF-8 in a confined `Arena` per call, bound with `sqlite3_bind_text(stmt, i, ptr, nbytes, SQLITE_TRANSIENT)`; `SQLITE_TRANSIENT` is the pointer value -1 (`MemorySegment.ofAddress(-1)`), so SQLite copies and the arena can close right after the bind (CPython also binds transient). Blobs the same way from `IoUtil.bytesLike`. `int` is `Long`, or `BigInteger` -> OverflowError with the measured text; `float` -> `bind_double`; `None` -> `bind_null`; anything else goes through the adapter protocol (`__conform__`, `adapters[(type, PrepareProtocol)]`) first.
- Text out: `column_text` + `column_bytes` copied out at once, decoded as strict UTF-8 for `text_factory is str` (failure text measured above), `bytes`/`bytearray` handed the raw bytes, any other callable called with `bytes`. Declared types for `PARSE_DECLTYPES` from `sqlite3_column_decltype`, `PARSE_COLNAMES` from the `[type]` suffix of the column name.
- SQL text containing NUL -> the measured ProgrammingError before calling SQLite. "One statement at a time" from the `pzTail` out-parameter of `prepare_v2` (skip trailing white space and comments as CPython does).
- Statement cache: an access-ordered `LinkedHashMap` of `cached_statements` entries keyed by the SQL string; a cached statement that is still busy (`in_use`) is not reused, a fresh one is prepared, as in `connection.c`.
- Transaction control: legacy mode (`autocommit == -1`) issues `BEGIN <isolation_level>` before INSERT/UPDATE/DELETE/REPLACE when `sqlite3_get_autocommit` says no transaction is open (statement kind from the first keyword, as CPython does, not from `stmt_readonly`); `autocommit=False` keeps a transaction always open (PEP 249), `True` never opens one; `executescript` commits first in legacy mode; `__exit__` commits or rolls back.

Upcalls (the part where FFM replaces C function pointers):
- A fixed set of global stubs created once with `LINKER.upcallStub(..., Arena.global())`, never one per Python callable: `xFunc(ctx, argc, argv)`, `xStep`, `xFinal(ctx)`, `xValue(ctx)`, `xInverse(ctx, argc, argv)`, `xDestroy(void*)`, collation `xCompare(void*, int, void*, int, void*) -> int`, authorizer `(void*, int, char*, char*, char*, char*) -> int`, progress `(void*) -> int`, trace `(unsigned, void*, void*, void*) -> int`. Ten stubs.
- The `void*` user data is not a pointer but an id into a `ConcurrentHashMap<Long, CallbackCtx>` (the `WindowsIocp` wait-context pattern). `CallbackCtx` holds the Python callable and the connection's state. SQLite calls `xDestroy` when a function or collation is replaced or the connection closes; the stub removes the map entry, which gives the same lifetime CPython gets from its destructor callback.
- Aggregates: per-group state is 8 bytes from `sqlite3_aggregate_context`, holding an id into a second map (instance of the aggregate class); `xFinal` removes it.
- Arguments are read with `sqlite3_value_type` and the matching accessor; results are written with `sqlite3_result_*` (text and blob transient).
- **No exception may leave an upcall** (it would terminate the JVM): every stub body is `try { ... } catch (Throwable t)`. A Python exception is turned into the SQLite error of the table in section 3 (`sqlite3_result_error`, `SQLITE_DENY`, non-zero from the progress handler) and, when tracebacks are enabled, reported through `sys.unraisablehook`. For the collation case, where CPython leaves the Python exception set, the stub stores it in the connection's `pendingException` slot and the Java code that made the `sqlite3_step` call rethrows it when the call returns. `StackOverflowError` inside a callback is caught the same way and becomes RecursionError at the caller.
- Upcalls run synchronously on the thread that is inside `sqlite3_step`, so Python-level thread state (current exception, context variables, recursion depth) is simply that thread's. A callback may run SQL on the same connection (a nested downcall); the cursor-level "recursive use" check is kept in Java.

## 6. Threads, finalization, memory ownership
- There is no GIL. SQLite is built `THREADSAFE=1` (serialized), which is what `threadsafety == 3` promises, so the library tolerates concurrent calls on one connection. pyJVM's own per-connection state (statement cache, cursor list, callback ids, `pendingException`) does not: each connection gets a `ReentrantLock`, taken around every operation, reentrant because callbacks re-enter. It is not held across anything but that connection's own calls, so two connections never block each other.
- `check_same_thread=True` compares `Thread.currentThread().threadId()` with the creating thread and raises the measured ProgrammingError; the Cleaner thread is exempt (it only finalizes).
- Blocking: `sqlite3_step` can sit in SQLite's busy handler for `timeout` seconds, and `backup` sleeps between steps. A Python signal handler cannot run meanwhile; it runs when the call returns, which is also what CPython's main thread sees. `Connection.interrupt()` from another thread works as in CPython. No slice-polling is added here.
- Ownership: native state objects (`DbState`: the `sqlite3*`, the set of live `sqlite3_stmt*` and `sqlite3_blob*`, callback ids) never reference the Python objects. `close()` finalizes statements, closes blobs, then calls `sqlite3_close_v2`. A static daemon `Cleaner` does the same for a connection that was dropped without `close()`; `close_v2` is used so that order problems leave a zombie handle instead of an error. Cursors and statements dropped alone only reset or finalize their statement. No `Arena` per object; per-call confined arenas for strings and out-parameters.
- Deviations from CPython to document in `JVM_BACKEND.md`: a dropped connection is closed at some later collection, not at once, so on Windows the database file stays locked (`os.remove` fails with PermissionError) until then, and an uncommitted transaction is rolled back late; the `ResourceWarning` for an unclosed connection is emitted from the delivery queue of the creating thread (`WeakrefDelivery.post`), late, or not at all at exit. Possible mitigation, to be decided after the test baseline: keep a registry of open-but-unreachable-candidates and, like `_winapi.CreateProcess`, run one collection when a path-level operation on Windows fails with a sharing violation while connections are open.
- `load_extension` runs arbitrary native code inside the JVM process: off by default (SQLite's default), enabled only through `enable_load_extension(True)`, with the audit events CPython raises (`sqlite3.connect`, `sqlite3.connect/handle`, `sqlite3.enable_load_extension`, `sqlite3.load_extension`; add them to `AuditEvents.java`).

- `sqlite3_types`, `sqlite3_row`: adapters and converters with both detect flags, `text_factory` variants, invalid UTF-8, big ints, `Row` access forms, equality and hash.
- `sqlite3_callbacks`: each row of the callback table, a deterministic function, an aggregate, a window function, a collation used by ORDER BY, an authorizer that denies one table, a progress handler that interrupts, a trace callback that collects statements, a function that queries the same connection.
- `sqlite3_blob`, `sqlite3_backup_serialize`: blob read/write/seek/slicing and its errors; backup with a progress callback; serialize into a second connection; `iterdump` text.
- Lane-specific behaviour (positional and keyword deprecations, `version`, `SQLITE_KEYWORDS`) lives in the cases behind `sys.version_info` branches, as existing cases do.

## 10. Risks and open questions
1. **A C build enters the project.** Until now nothing in the tree is compiled from C; the vendored amalgamation needs a C compiler on the developer machine and in CI, before the R2-01 tooling exists. If that is unwelcome right now, the interim is to run on the fallback (system library / `winsqlite3.dll` / `PYJVM_SQLITE3`), with the measured gaps of `winsqlite3.dll`.
2. Upcalls: an uncaught throwable, or a stub invoked after its context is gone, ends the JVM. Mitigation: the catch-all rule, ids instead of pointers (a stale id is a map miss, not a dangling pointer), stubs never freed.
3. Late finalization (section 6) will show up in CPython's tests and in user code that relies on `del con`. Mitigation is documented behaviour plus the optional collect-on-sharing-violation hook.
4. `str` is UTF-16 today: lone surrogates and non-BMP text must round-trip through UTF-8 exactly as CPython's; re-check when P2-03 lands.
5. Free-threaded use: CPython's own `_sqlite3` is still being hardened for the free-threaded build; the per-connection lock is pyJVM's answer. Deadlock risk if a callback on thread A waits for thread B, which is blocked on the same connection's lock (CPython with the GIL released around `sqlite3_step` would let B proceed into SQLite's own mutex and block there too, so the behaviour is equivalent, but check).
6. Per-row cost: each column costs two to three downcalls. Measure on a 100k-row select before optimising.
7. Unverified items: everything on Linux; `util.c`'s error map; whether a native exception class can be created with module `sqlite3`; the C compiler on this machine; `datetime` on pyJVM; package support in `run_cpython_test.py`.

Questions for the owner:
- a. Commit the amalgamation source (about 9 MB, 260k lines) under `third_party/sqlite/`, or fetch it by pinned hash at build time and commit only the hash and the build script? (Recommended: commit it; vendoring means the source is in the tree and reviewable.)
- b. One pinned SQLite for all lanes (recommended: the lane selects language behaviour, not the library), or track each CPython lane's bundled version (3.50.4 for 3.13/3.14, 3.53.4 for 3.15)?
- c. May the system library remain as an automatic fallback (recommended, with the version floor), or should a missing vendored build be a hard `ImportError`?
- d. `load_extension`: keep it, as every CPython lane has it, or leave it absent because it loads arbitrary native code into the JVM?
- e. Is a C compiler acceptable as a build prerequisite now, or should the vendored build wait for R2-01's native tooling while the module starts on the fallback?
