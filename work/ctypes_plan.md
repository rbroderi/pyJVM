# Plan: `_ctypes` for pyJVM (phase N6c of `native_modules_plan.md`, ticket R4-01 of `NATIVE_EXTENSIONS_PLAN.md`; written by a planning agent, 2026-11-16)

Planning only: nothing is implemented and nothing was built or run on pyJVM. Measured with one-off scripts on `C:\Python313` (3.13.17), `C:\Python314` (3.14.10), `C:\Python315` (3.15.2), all Windows x64, and read from CPython's sources (`Lib/ctypes` in the checkout; `Modules/_ctypes/*.c` with `git show`). The Linux side of every table is **unverified**. Per the decisions of 2026-11-16 this module **waits for the R2-01 native loader**; `_sqlite3` and `_curses` go first.

## 1. Goal and scope
`import ctypes` works on Windows x64 and Linux x86-64 glibc on the three lanes, with CPython's `Lib/ctypes` (`__init__.py`, `_endian.py`, `_layout.py` on 3.14+, `util.py`, `wintypes.py`) unmodified on a Java `_ctypes`: loading libraries, calling C functions with CPython's conversion rules, structures/unions/arrays/pointers with the platform layout, callbacks, `errno`/`GetLastError` handling, and the buffer protocol on ctypes objects. Unblocks 12 modules on 3.13 and 11 on 3.15 (`STDLIB_STATUS.md:42, 77`), among them `_pyrepl.windows_console` (the Windows REPL), `_pyrepl._minimal_curses`, `ctypes.util`, and optional users (`uuid`, `multiprocessing.sharedctypes`).
Out of scope, and absent or raising rather than faked: the CPython C API through ctypes (`pythonapi` functions, `PyObj_FromPtr`, `Py_INCREF`/`Py_DECREF`: there is no `PyObject*` here until track C's shim exists), COM support beyond what `ctypes/__init__` imports (`COMError`, `CopyComPointer`, `_check_HRESULT`, `FormatError` are provided; `DllGetClassObject`/`DllCanUnloadNow` are Python functions that import `comtypes`), 32-bit calling conventions, big-endian hosts, AIX/macOS helper modules.
Prerequisites: **R2-01** (library loader, extraction cache, native-access configuration, Rust in CI) and, for the engine recommended in section 5, a small Rust helper built by that tooling. R4-01 also names P3-05 (`unittest`/`test.support`, for `test_ctypes`). `ctypes.util.find_library` on Linux needs N1 (`subprocess` for `ldconfig`/`gcc`). No dependency on N0 for the core.

## 5. Design
### C1. The call engine: vendored libffi behind one helper (recommended), not FFM-generated downcalls
`native_modules_plan.md` N6 said "FFM covers it without Rust: `CFuncPtr` calls as downcall handles built from `argtypes`/`restype`". Two things changed: `_ctypes` now waits for R2-01 anyway, so a native helper costs no extra infrastructure, and the vendoring policy says not to hand-roll what a vetted library does. The comparison:

| Concern | FFM downcall handle per signature | libffi through `pyjvm_ffi_call` |
| --- | --- | --- |
| Who knows the ABI | the JDK's linker (vetted, but a different implementation from CPython's) | libffi, the same code CPython calls: same classification, same quirks |
| `errno` / `GetLastError` (`use_errno`, `use_last_error`) | `captureCallState` returns the value after the call, but ctypes swaps its private copy **into** `errno` before the call as well; from Java that needs a second native call, between which the JVM may run libc code (**believed**, spike S2) | swap, call, swap back inside one native function, exactly `callproc.c` |
| Variadic functions | must be declared with `firstVariadicArg(n)`; ctypes knows `n` only when `argtypes` is set and more arguments are passed (`callproc.c:873`); what an undeclared call does to `%al` on SysV and to float duplication on Win64 is **unverified** | `ffi_prep_cif_var` in the same case CPython uses it; otherwise identical to CPython by construction |
| `long double` (16-byte x87 on Linux), `_Complex` (3.14+ `F D G` on Linux) | no FFM layout for either: cannot be passed or returned | supported by libffi |
| Structs and unions by value | `GroupLayout`; refuses non-natural alignment (packed structs), unions classified by the JDK | as CPython (which itself restricts unions and bit-fields by value) |
| Callbacks | one upcall stub per `CFUNCTYPE` instance (code-cache memory per callback, freed with its arena) | `ffi_closure` per callback; one global FFM upcall stub `(cif, ret, args, userdata)` for all of them |
| Speed | JIT-inlined downcall, fastest | one fixed downcall plus libffi's dispatch; like CPython's, far below the cost of the Python-level conversion around it |
| Needs a native artefact | no | yes: the helper for windows-x86_64 and linux-x86_64 |
Recommendation: libffi as the single engine. It gives CPython's behaviour by construction where FFM gives a second, slightly different one, and it matches the policy. The Java side is written against a small interface (`prepare(cif description)`, `call(cif, fn, args, ret, flags, errState)`, `closure(cif, id)`), so an FFM-only engine remains possible later as a no-native-artefact fallback for the plain integer/pointer/double subset; it is not part of this plan's sizing. Spikes S1-S3 confirm or overturn the "believed" cells before step 3.

How a call runs (mirrors `_ctypes_callproc`): convert each Python argument with the `argtypes` `from_param` converters (or the default rules: `int` -> C int, `bytes` -> `char*`, `str` -> `wchar_t*`, `None` -> NULL, ctypes instances by value or pointer, `_as_parameter_`), writing values into a per-call native block; build or fetch the cached `ffi_cif` for (ABI, return type, argument types); one downcall `pyjvm_ffi_call(cif, fn, ret, argv, flags, state)`; convert the result through `restype` (a ctypes type, a callable, or None), then `errcheck`, then out-parameters (`paramflags`). `ffi_type` descriptions are plain C structs (`size`, `alignment`, `type`, `elements`) that Java writes into native memory once per ctypes type; the helper exports the addresses of the built-in ones. The private errno and last-error copies are per thread (a `ThreadLocal` native cell passed as `state`). `FUNCFLAG_HRESULT` and `_check_HRESULT` raise `OSError` through `WindowsNative.winError`. Windows structured exceptions (an access violation in the callee) are turned into `OSError` by CPython's SEH wrapper; HotSpot instead reports a fatal error: documented difference, no attempt to catch.

### C2. Memory model
- Every ctypes instance owns or borrows a block of **native** memory: `CMem { long address; long size; boolean owned; Object base; }` with a `MemorySegment` view. Owned blocks come from `calloc` and are freed by a `Cleaner` whose state does not reference the Python object. `_b_base_` keeps the owner alive for sub-objects (a struct field view, an array element); `_objects` keeps Python objects alive whose memory the block points to (`c_char_p(b"x")` holds the bytes copy; a pointer holds its target), exactly CPython's keep-alive tree, which matters more here because the GC would otherwise free them at an arbitrary time.
- Python `bytes`/`str` passed to a call are copied into the per-call block (NUL-terminated; `str` as UTF-16 code units on Windows, UTF-32 on Linux) and freed after the call. C code that keeps such a pointer sees freed memory, as it would in CPython once the object dies; `c_char_p`/`c_wchar_p` instances keep their copy in `_objects`.
- `addressof`, `byref`, `pointer`, `cast`, `string_at`, `wstring_at`, `memmove`, `memset`, `resize`, `from_address`, `in_dll` operate on real addresses. `from_buffer_copy` copies in. `from_buffer(obj)` must **share** memory with a Python object, which has no address here (section 2): supported when the source is itself a ctypes object or another native-backed buffer; for `bytearray`, `array.array` and `memoryview` over them it raises `TypeError`/`BufferError` with a pyJVM-specific text and is listed as unsupported (question c; the alternative is to give `bytearray` a native-capable store, a core-runtime change).
- `py_object` (`'O'`): the 8-byte slot holds an id into a global handle table (`long` -> object), never an address. `_cast_addr`, `_string_at_addr`, `_wstring_at_addr`, `_memoryview_at_addr` are reserved, distinct, non-callable addresses (cells allocated at init); `CFuncPtr.__call__` recognises them and runs the Java implementation directly, so `ctypes.cast`, `string_at`, `wstring_at`, `memoryview_at` work without a `PyObject*`. Any other `PYFUNCTYPE`/`PyDLL` call raises a clear error ("pyJVM has no CPython C API: ... cannot be called through ctypes"). `_memmove_addr`/`_memset_addr` are the C library's real functions.
- `pythonapi`: on Linux `PyDLL(None)` is `dlopen(NULL)` and works as a handle (attribute lookups of `Py*` fail with the normal `AttributeError`). On Windows `ctypes/__init__.py:551` reads `sys.dllhandle`; proposal: provide it as the module handle of the process's `jvm.dll` (a real handle of "the DLL that implements the interpreter"; `Py*` lookups fail normally). This is the one place a value has to be chosen: question d.

### C3. Types and layout
- Metaclasses in Java (after spike S0; fallback: the class layer as embedded Python source over Java primitives, the `TypingSource`/`_typing` precedent, with helper names removed from the module). Each ctypes class carries a Java `StgInfo` (size, alignment, length, `ffi_type` address, getter/setter, format string, flags, pointer target, argtypes/restype for function types), CPython's "stginfo".
- Simple types: one getter/setter pair per type code over `MemorySegment` (`ValueLayout` unaligned variants), with CPython's range behaviour (silent truncation on store, sign rules), `c_bool`, `c_char`/`c_wchar` (UTF-16 surrogate pairs on Windows as CPython does), `z`/`Z`/`P` pointer rules, `c_longdouble` (on Windows a double; on Linux 80-bit extended converted to and from Java `double` in Java), `X` (BSTR) and `v` (VARIANT_BOOL) on Windows, byte-swapped variants (`__ctype_be__`/`__ctype_le__`) for `_endian.py`.
- Structures and unions: on 3.14+ `_ctypes` calls `ctypes._layout.get_layout` exactly as CPython does (`gcc-sysv` and `ms` modes, `_pack_`, `_align_`, `_layout_`, bit-fields) and creates `CField` objects from its result, so layout and its error messages come from CPython's own Python code. On 3.13 the same rules are a Java port of 3.13's `cfield.c:PyCField_FromDesc` (~250 lines), checked against the 3.14+ path with a generated corpus. `_anonymous_`, inheritance of `_fields_`, `_fields_ is final`, incomplete types and `SetPointerType`/`set_type`, positional and keyword `__init__`.
- Arrays (`T * n` cached per (type, length)), pointers (`POINTER` cache: C-level on 3.13, Python-level `__pointer_type__` protocol on 3.14+), `c_char`/`c_wchar` array `value`/`raw`, slicing, negative and out-of-range index rules.
- Buffer export: `_CData` implements `PyByteSequence` over its segment for reads, and a new small interface (`setUnsigned`) that `PyMemoryView.readonly()`/`setUnsigned` (`PyMemoryView.java:38-42`) and `IoUtil.fill` (`IoUtil.java:51-58`) accept besides `PyByteArray`, so `memoryview(ctypes_obj)`, `file.readinto(buf)` and `bytes(buf)` work. Multi-character formats, `shape`, `itemsize` and `ndim` for `test_pep3118` need `PyMemoryView` to carry a format string and shape: a separate, later step that touches a core class.
- Pickling (`__reduce__`, `_unpickle`), `repr`, `__bool__`, `ArgumentError`, `COMError(hresult, text, details)`.

### C4. Callbacks
`CFUNCTYPE(...)(python_callable)` allocates an `ffi_closure` bound to the helper's trampoline with an id as user data; the trampoline calls the single global FFM upcall stub `void cb(ffi_cif*, void* ret, void** args, long id)`. Java looks the id up in a `ConcurrentHashMap` (callable, converters, restype setter, flags), converts arguments, calls Python, stores the result. The catch-all rule applies: any `Throwable` is caught, reported through `sys.unraisablehook` with CPython's wording ("Exception ignored on calling ctypes callback function ...", measure per lane), and the return slot is zeroed. The closure and map entry live exactly as long as the Python `CFuncPtr` object (Cleaner frees both); C code that calls a callback after its Python object was collected jumps into freed memory, as in CPython, but here "collected" happens at an unpredictable time rather than at the last `del`: users must keep a reference, the same rule the ctypes documentation already states. Callbacks arriving on a thread the JVM has never seen are attached by the JVM for the duration of the upcall (the `WindowsIocp` wait callback already relies on this); such a thread has no Python thread state (no `threading` identity, signal handlers do not run there). `use_errno`/`use_last_error` swaps around the callback happen in the helper trampoline.

### C5. Loading
`dlopen(name, mode)` / `LoadLibrary(name, winmode)` are called directly (not `SymbolLookup.libraryLookup`, which hides the handle and the mode flags ctypes exposes) and return the handle as an int; `dlsym`/`GetProcAddress` (by name or ordinal) resolve functions and `in_dll` data; `dlclose`/`FreeLibrary` are exposed but nothing is unloaded implicitly. `dlopen` errors use `dlerror()` text in `OSError`; Windows errors use the measured `FileNotFoundError` text. `dllist` on Linux 3.14+ through `dl_iterate_phdr` with an upcall. R2-01 supplies native-access configuration and the cache from which the helper library itself is loaded. Audit events `ctypes.dlopen`, `ctypes.dlsym`, `ctypes.dlsym/handle`, `ctypes.call_function`, `ctypes.cdata`, `ctypes.cdata/buffer`, `ctypes.addressof`, `ctypes.string_at`, `ctypes.wstring_at`, `ctypes.get_errno`/`set_errno`, `ctypes.get_last_error`/`set_last_error`, `ctypes.seh_exception` (not raised), `ctypes.create_string_buffer` (raised from Python): add the native ones to `AuditEvents.java` and remove `ctypes.*` from the "not raised" list in `JVM_BACKEND.md`.

## 6. Threads, finalization, ownership
- No GIL: CPython releases it around every foreign call (except `PyDLL`), so C code already sees concurrent callers; nothing to add. ctypes objects themselves are not synchronised in CPython's default build either; the Java state that must not corrupt (type caches, the handle table, the callback map, the cif cache) uses concurrent maps.
- A blocking C function cannot be interrupted by a Python signal handler until it returns (same as CPython's main thread, where the handler also runs after the call).
- Crash surface: ctypes can crash CPython; here a wild pointer brings down the JVM with an `hs_err` file instead of a Python traceback (`faulthandler` does not exist on pyJVM). State this in `JVM_BACKEND.md`.
- Ownership summary: native blocks by `Cleaner`; keep-alive through `_objects`/`_b_base_`; closures by `Cleaner`; loaded libraries never unloaded implicitly; per-call arenas for argument blocks.

## 10. Risks and open questions
1. **Size and depth.** This is the largest native module by far, and the type layer must reproduce a metaclass-heavy C design on an object model that has never hosted a native metaclass (S0). If S0 fails, the Python-source fallback changes steps 2 and 4.
2. **No object addresses.** Everything in ctypes that assumes a Python object has stable memory is affected: `from_buffer` on `bytearray`/`array`, `py_object`, `pythonapi`, `id()`-based tricks, `PyObj_FromPtr`. These are refused with clear errors, not approximated; some popular recipes (zero-copy `from_buffer(bytearray)`) will not work until the runtime has a native-capable byte store.
3. **GC-timed lifetime** of callbacks and owned memory: programs that are correct on CPython only because of reference counting (a temporary callback passed to C and used during that call is fine; one stored by C is a bug on both, but shows up differently) and `test_ctypes` cases that count references will differ.
4. A wrong call crashes the JVM, with no `faulthandler` and no Windows SEH conversion to `OSError`.
5. The engine comparison in C1 contains unverified cells (errno clobbering between FFM calls, variadic behaviour without the option, packed structs); S1-S3 must run before step 3. The libffi build on MSVC through `libffi-sys` is **unverified**.
6. `test_ctypes` depends on `_ctypes_test` (group ii above); without the test-only build, well under half of the suite can run.
7. `str` is UTF-16: `c_wchar` on Linux is 32-bit, so conversion is by code point; lone surrogates need CPython's exact rule; recheck after P2-03.
8. Dependencies outside this plan: R2-01 (and with it Rust in CI), P3-05 for the test suite, N1 for `find_library` on Linux, a core change to `PyMemoryView` for PEP 3118.
9. Everything about Linux in sections 3 and 5 is unverified; the Windows measurements were made on python.org-style builds in `C:\Python31x`, not on the uv-managed interpreters the lanes use (3.13.17 here against 3.13.18 in `.venv313`).

Questions for the owner:
- a. Engine: vendored libffi behind a Rust helper (recommended, C1), or FFM-generated downcalls with the listed gaps (`long double`, complex, errno pre-set, packed structs by value) and no native artefact?
- b. Type layer: in-house Java port (recommended, for per-lane fidelity), or vendor PyPy's MIT-licensed `_ctypes` Python package and patch it per lane (less code to write, weaker match with CPython's messages and 3.14+ `CField`/`_layout` behaviour)?
- c. `from_buffer(bytearray)`: refuse for now (recommended), or schedule a native-capable `bytearray` store in the core runtime first?
- d. `sys.dllhandle` on Windows: the `jvm.dll` module handle (recommended), or the process executable's handle, or leave `sys.dllhandle` absent and special-case it some other way? It must exist for `import ctypes` to succeed with the unmodified `Lib/ctypes/__init__.py`.
- e. Is "after R2-01" strict, or may steps 0-2 (which need only FFM plus, under option a, the helper) start as soon as the loader slice of R2-01 exists, before R2-02 onwards?
- f. Should the test-only `_ctypes_test` build wait for track C's shim (where the unmodified extension would load), or be built against a stub header now?
