# Plan: native modules (HANDOFF open item 5; written by a planning agent, 2026-11-16)

Covers, in the order HANDOFF gives: POSIX `_socket`, `_posixsubprocess`, `resource`, `fcntl`, `pwd`, `grp` (import-only shells today), then the `_typing` review, `_ctypes`, the CJK `_codecs_*`, `_curses`, `_sqlite3`. This is a phased roadmap, not one work item: each phase below should get its own detailed plan in the style of `overlapped_plan.md` before coding (surface tables measured on Linux CPython, spikes). What is fixed here: the implementation route per module, the order and dependencies, sizes, risks and how each phase is verified.

Policy applied (HANDOFF item 5 and "Standing decisions"): pure Java where Java suffices; FFM (`java.lang.foreign`, Java 25) for anything libc- or library-shaped; Rust only under `NATIVE_EXTENSIONS_PLAN.md` (the extension ABI and the C-API shim), which none of these modules needs; per-OS classes (`Posix*` / `Windows*`); errors captured per call with `Linker.Option.captureCallState("errno")` (POSIX) or `("GetLastError")`/`("WSAGetLastError")` (Windows); no placeholders: a function that is not implemented is absent or raises a clear CPython-style error; POSIX-only modules stay `ModuleNotFoundError` on Windows.

## Decisions (2026-11-16)
Made by the owner after this plan was written; where the text below still says "recommended", "assumes" or "open question" on these points, this section wins.
1. **N0 (D1): option (b).** Every POSIX descriptor is a real kernel descriptor through FFM. No hybrid table; option (a) is dropped, including as a fallback (risk 1).
2. **Spawning (D2):** `posix_spawn` now. A small Rust spawn helper comes later for `preexec_fn`, `uid`/`gid`/`extra_groups` and `umask`; until it exists those arguments raise the clear error D2 describes. This settles the open question in D2 and risk 2 (the helper is a later phase, under `rust/` per `NATIVE_EXTENSIONS_PLAN.md`).
3. **POSIX target (D4):** Linux x86-64 glibc only, plus Windows, which the project already supports. aarch64, musl and macOS stay unsupported hosts that fail loudly at module init (settles risk 4).
4. **N6 order:** `_sqlite3` and `_curses` go first; `_ctypes` waits for the R2-01 native loader (settles risk 8; the "loader slice first" assumption stands). Detailed plans: `sqlite3_plan.md`, `curses_plan.md`, `ctypes_plan.md` in this directory.
5. **Vendoring policy:** small pieces are written in-house; a large or security-sensitive item vendors a vetted library instead of being hand-rolled: only the parts needed, shaded (private names, no symbols leaked into or taken from the process), and listed in `THIRD_PARTY_LICENSES`. Each N6 plan states what it vendors, what it binds from the system, and the licence consequence. This revises two sentences of the N6 summary in section 3: `_sqlite3` binds a vendored SQLite build by default (the system library is the fallback, not the default), and `_ctypes` is no longer "FFM without Rust" by assumption (see `ctypes_plan.md`, decision C1).

## 2. Key design decisions
### D1. POSIX descriptors become kernel descriptors (phase N0). Everything else in the POSIX half depends on it.
`fork_exec`, `fcntl`, sockets, `select`/`poll`, `set_inheritable`, terminals and `pass_fds` all take descriptor numbers that must mean the same thing to the kernel and to a child process. Two ways:
- (a) Hybrid, as Windows did: keep the `FileChannel` table and add an "OS-backed" entry kind (pipes, sockets), translating numbers when spawning. Smaller, but a regular file opened by Python has no kernel descriptor the runtime can reach (java.nio does not expose it), so `subprocess.run(cmd, stdout=f)` would need a second, independent open of the path (the "shadow handle" Windows uses for `msvcrt.get_osfhandle`): the offset is not shared, so the parent overwrites the child's output on its next write. `fcntl.flock(f)`, `os.fstat` identity, `select` on mixed descriptors would each need the same trick.
- (b) **Recommended:** on POSIX, `IoFd` entries *are* kernel descriptors: `open`, `close`, `read`, `write`, `pread`/`pwrite`, `lseek`, `fstat`, `ftruncate`, `fsync`, `dup`, `dup2`, `pipe2`, `isatty` go to libc through FFM in a new `PosixFds` (FFM layer in `PosixNative`), and the Python-visible number is the kernel's. `IoFd` keeps its static API and dispatches on `ImportSupport.WINDOWS`; the Windows side is untouched. Errors come from `errno` directly instead of translating `IOException` (better fidelity: today's messages are reconstructed). `O_CLOEXEC` on every open (PEP 446), so `get_inheritable`/`set_inheritable` become real (`fcntl(F_GETFD/F_SETFD)`).
Cost of (b): every file read and write on POSIX crosses FFM with a copy between heap and native memory (use a per-thread reusable native buffer; `_io` buffers above it, so calls are large). Path-based functions (`stat`, `listdir`, `rename`, ...) can stay on java.nio in this phase.
Decision needed from the owner only if (b)'s regression surface is unwelcome: it changes the engine under every POSIX file test. This plan assumes (b).

### D2. Process creation uses `posix_spawn`, never `fork` from the JVM.
After `fork()` in a multi-threaded JVM the child has one thread and may only call async-signal-safe functions; it cannot run Java (no GC or compiler threads, any safepoint deadlocks). The JDK itself spawns through `posix_spawn` and a helper for this reason. So:
- `os.fork`, `forkpty`, `os.exec*` stay absent. `subprocess`'s `preexec_fn` cannot be supported: `fork_exec` raises a clear error when it is not None (text to settle in the phase plan, e.g. `RuntimeError("preexec_fn is not supported by pyJVM: the JVM cannot run Python code in a forked child")`; CPython itself raises RuntimeError for `preexec_fn` in subinterpreters, the closest precedent).
- `fork_exec` is implemented on `posix_spawn` with file actions and attributes: stdio `dup2` sequence in the order `_posixsubprocess.c: child_exec` uses (including the "descriptor is already 0/1/2" shuffles), `posix_spawn_file_actions_addchdir_np` (glibc 2.29), `addclosefrom_np` (glibc 2.34) or explicit `addclose` for every open descriptor not in `fds_to_keep` (list `/proc/self/fd` in the parent; anything opened concurrently is `O_CLOEXEC`), `adddup2(fd, fd)` to clear close-on-exec on `pass_fds`, `POSIX_SPAWN_SETSIGDEF` for `restore_signals` (SIGPIPE, SIGXFSZ), `POSIX_SPAWN_SETSIGMASK` with an empty mask (the calling JVM thread's mask must not leak), `POSIX_SPAWN_SETSID` (glibc 2.26) for `start_new_session`, `POSIX_SPAWN_SETPGROUP` for `process_group`.
- Not expressible with `posix_spawn`: `uid`, `gid`, `extra_groups`, `umask`. First version: raise a clear NotImplementedError naming the argument. If they are wanted later, the faithful route is a tiny spawn-helper executable (what `jspawnhelper` is for the JDK) that performs CPython's exact child sequence; that would be the one place native code outside FFM enters, and by policy it would be Rust under `rust/` per `NATIVE_EXTENSIONS_PLAN.md`. **Open question for the owner; not in this plan's scope.**
- The executable list: `fork_exec` receives every PATH candidate; try each with `posix_spawn` in the parent, continue on ENOENT/ENOTDIR, remember the last other errno (same rule as the C loop).
- Error protocol: `subprocess._execute_child` (cpython `Lib/subprocess.py:2052-2125`) reads `b"OSError:<hex errno>:<msg>"` from `errpipe_read` and builds the exception with the right filename (`noexec:chdir` selects `cwd`). `posix_spawn` reports exec failure as its return value, so `fork_exec` writes that record into `errpipe_write` itself and returns a pid that is not a child; `subprocess` then calls `os.waitpid(pid, 0)` inside `except ChildProcessError: pass` (`:2118-2125`), which a real `waitpid` answers with ECHILD. Distinguish `chdir` failure by checking `cwd` in the parent first (stat + search permission) when a spawn with a chdir action fails. This keeps the user-visible exception identical to CPython's without a helper process. Spike it first (section 6, S2).
- Environment: when `env_list` is None the child must get libc's `environ` (read the C global at call time), not Java's start-up snapshot. `putenv_child_plan.md` tests exactly this.
- `subprocess` prefers `os.posix_spawn` when `_use_posix_spawn()` is true (`Lib/subprocess.py:816-861, 929-930, 2026-2045`: needs `os.posix_spawn`, `os.confstr('CS_GNU_LIBC_VERSION')` >= 2.24, and `os.POSIX_SPAWN_CLOSEFROM` for `close_fds=True`). Provide `os.posix_spawn`/`posix_spawnp` with the same machinery so both paths are covered; `fork_exec` is still required (any `cwd`, bare program names, `pass_fds`, `start_new_session`).
- Lane difference: 3.13 calls `fork_exec` with 23 arguments (a trailing `allow_vfork`, `C:\Python313\Lib\subprocess.py:1922-1931`); 3.14 and 3.15 pass 22. Gate the arity with `LangVersion`.

### D3. Sockets are FFM libc sockets, not `java.nio.channels`.
java.nio sockets have no descriptor number (`fileno()`, `select`, `socket(fileno=)`, `dup`, inheritance), no datagram/raw generality, no `socketpair`, and options are an allow-list. Windows already took the FFM route; POSIX follows with `PosixSockets` + `PosixSocketModule`, and the logic that is not OS-specific in `WindowsSocketModule` (argument parsing, address tuple <-> sockaddr, timeout state machine, `gaierror`/`herror` classes, default timeout) moves to a shared `SocketCommon` so that Windows phase C (`overlapped_plan.md`) and POSIX grow from one place.

### D4. Constants and struct layouts are generated, per OS, from CPython and from the C headers.
The stubs carry hand-typed Linux x86-64 values. Real modules need a few hundred (`socket` ~400 names, `fcntl` ~100, `resource` ~25, `termios` ~250). Generate tables with scratch scripts run under Linux CPython in WSL (`{n: getattr(mod, n) for n in dir(mod) if isinstance(..., int)}`), as the Windows tables were (HANDOFF "What 46f8e0f contains", item 2). This time **commit the generators** under `tools/` (the Windows ones were lost with `E:\pyjvm-work`). Struct offsets (`struct flock`, `rlimit`, `rusage`, `passwd`, `group`, `sockaddr_*`, `addrinfo`, `termios`, `pollfd`, `epoll_event`) are written by hand for Linux LP64 and asserted at class init against a C-computed size where libc offers one. Supported POSIX target for this plan: **Linux x86-64 glibc** (the WSL gate host). aarch64 Linux shares the struct layouts used here but not all constants (`O_DIRECTORY`, `O_NOFOLLOW`, `O_DIRECT`, `O_LARGEFILE` differ); musl lacks the `_np` spawn actions; macOS differs in layouts and values. Record these as unsupported hosts rather than guessing; each module's class init should fail loudly (ImportError with the reason) on an unrecognised `os.arch`/libc.

### D5. Blocking calls and signals.
There is no GIL to release, so blocking FFM calls are simply called. A Python signal handler cannot run while a thread is parked in native code; CPython's blocking calls return EINTR and retry after running handlers. Follow the Windows precedent (`JVM_BACKEND.md` "Windows overlapped I/O": `select` in 50 ms slices; wakeup fd): wait with `poll(2)` in slices before a blocking `read`/`recv`/`accept`/`waitpid` on the main thread and run pending handlers between slices. Settle the exact rule once in N0 and reuse it.

## 7. Risks and open questions
1. D1(b) replaces the engine under all POSIX file I/O. Mitigation: `IoFd` API unchanged, Linux gates before and after, the Windows path untouched. Fallback (a) is available but leaves known infidelities (shared offsets) and should be an explicit choice.
2. `fork`-less process creation: `preexec_fn`, `uid`/`gid`/`extra_groups`/`umask`, `os.fork` users (`multiprocessing` fork/forkserver start methods, `pty.fork`, `os.forkpty`) are out. A spawn helper (Rust, per the extension plan) would recover all but `preexec_fn`. Owner's call.
3. Nothing in this plan was measured on Linux: all Linux-side claims (struct offsets, glibc function availability by version, constant names, error texts, `_use_posix_spawn` behaviour) come from knowledge of glibc/CPython sources and must be re-measured in WSL by each phase's own plan. The WSL environment itself was not exercised (the Linux gates are paused, HANDOFF item 2). Items measured locally: the stubs' contents, the 22/23-argument `fork_exec` call, `_typing` names per lane, the JDK facts stated as certain in the hashlib plan only.
4. Host coverage: Linux x86-64 glibc only (D4). aarch64, musl and macOS need constants/layout tables and, for musl, alternatives to the `_np` spawn actions. If macOS is a first-tier platform for the runtime (the extension plan names four platforms for extension jars), say so before N0: `PosixFds` would then be written against a per-OS constants interface from the start.
5. Signals and blocking native calls (D5): the slice-polling rule costs latency and CPU when idle; check `time.sleep`, `Popen.wait`, `socket.accept` against Ctrl-C by hand.
6. Descriptor lifetime: sockets and pipes dropped without `close()` are closed by a `Cleaner` (as `WindowsSocketModule` does), later than CPython; a pipe write end kept alive by garbage delays EOF for a reader. POSIX `subprocess` closes explicitly, but user code that relies on refcount closing will hang where CPython does not; the JVM_BACKEND finalizer section should say so for POSIX too.
7. JVM-owned descriptors: `closefrom`-style closing in children is safe, but `os.closerange`/`os.close` on numbers the JVM itself owns (jar files, the JIT's perf map, sockets of a debugger) now really closes them. CPython has the same footgun with its own descriptors; do not guard, but never iterate "all descriptors" inside the runtime without the keep set.
8. `ctypes` sequencing against the Rust track (R2-01 first, or its loader slice only) and whether `_sqlite3` may depend on a system library that may be absent, are owner decisions; this plan assumes "loader slice first" and "yes, ImportError when absent".
9. Total size: roughly 7,000 lines of Java for N0-N5 (N0 900, N1 700, N2 1,100, N3 2,000, N4 small, N5 1,500 plus tables) and 10,000+ for N6, against about 2,900 lines for the whole Windows native layer written in waves 1-2. N0-N3 is of the order of two waves; N6 is a project per module.
