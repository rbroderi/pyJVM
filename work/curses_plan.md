# Plan: `_curses` and `_curses_panel` for pyJVM (phase N6b of `native_modules_plan.md`; written by a planning agent, 2026-11-16)

Planning only. `_curses` does not exist on Windows CPython (measured on `C:\Python313`, `C:\Python314`, `C:\Python315`: `import _curses`, `_curses_panel`, `curses`, `termios` and `readline` each raise `ModuleNotFoundError`), so **nothing in this plan was measured on a running interpreter**. The surface below was read out of CPython's C sources with `git show` (`v3.13.18`, `v3.14.10` and HEAD of the pinned 3.15 checkout, `Modules/_cursesmodule.c` and `Modules/_curses_panel.c`) by a regular-expression script, which can miss entries. Section 3 says how to get the real surface on Linux.

## 1. Goal and scope
On Linux x86-64 glibc (the only POSIX target, decision 3 of 2026-11-16), `import curses` works on the three lanes with CPython's `Lib/curses` unmodified: `curses.wrapper`, windows and pads, input, colours, the terminfo functions, and `curses.panel`. On Windows the modules stay absent, as in CPython: `_curses` and `_curses_panel` go to `POSIX_ONLY`. Unblocks 5 modules (`STDLIB_STATUS.md:48, 84`: `curses`, `curses.ascii`, `curses.has_key`, `curses.panel`, `curses.textpad`) and the curses route of `_pyrepl` on 3.13/3.14 (`_pyrepl.curses` tries `_curses`, then `curses`, then the ctypes-based `_minimal_curses`: `STDLIB_STATUS.md:105, 111`).
Prerequisites: **N0** (kernel descriptors: `setupterm(fd=...)`, `sys.stdout.fileno()`, and the pty the tests run under must be real descriptors) and **N2's `termios` and `os.openpty`** (to drive a pty in tests; `curses` itself does not import `termios`). The terminfo-only step (section 7, step 1) needs neither and can be built first.
`ROADMAP.md:136` lists `curses` as "explicitly unsupported"; this plan supersedes that row.

## 4. The native library: bound from the system, nothing vendored (recommendation; see question a)
- **Bound from the system:** `libncursesw.so.6` (wide-character ncurses, ABI 6), `libtinfo.so.6` (terminfo: `setupterm`, `tigetstr`, `tparm`, `putp`; split out on Debian/Ubuntu and a dependency of the former) and `libpanelw.so.6`, opened with `SymbolLookup.libraryLookup(name, Arena.global())` at `import _curses`. If one is missing: `ImportError` naming the file and the usual package (`libncursesw6`). Version floor: ncurses 6.1 (the `20170401` extended-colour functions the C module tests for, and `wgetdelay`); checked from `curses_version()`. Ubuntu 22.04 is believed to ship 6.3: **unverified**.
- **Why not vendored**, although ncurses is large and security-sensitive and the policy (decision 5) would point that way: (1) curses is useless without the host's terminfo database and must agree with it; a private ncurses still reads the system's `/usr/share/terminfo`, so vendoring removes no dependency on the host; (2) ncurses has no amalgamation: its build is autoconf plus generated sources, which does not fit "only the parts needed"; (3) the library handles untrusted terminal input and terminfo files, and the distribution patches it; a private copy would need pyJVM to track its CVEs; (4) CPython itself links the system ncurses on Linux distributions, so this is the faithful arrangement. The policy's intent is met either way: the large component is a vetted library, not hand-rolled code. What was considered and rejected as hand-rolling: a Java terminal library in its place (JLine, Lanterna: different semantics, new jars), and a Java terminfo parser with its own `tparm` for the `_pyrepl` subset.
- **Vendored alternative, if the owner wants no system dependency:** ncurses 6.x built statically with `-fPIC`, hidden visibility and a private name (`libpyjvm-ncursesw`), panel included, compiled with the system's terminfo directories. Licence: the ncurses licence, an MIT/X11-style permissive licence (copyright Free Software Foundation and Thomas E. Dickey), GPL-compatible; its copyright and permission notice must be reproduced, so it gets a `THIRD_PARTY_LICENSES` entry. Cost: an autoconf build in CI, security tracking, about one extra session.
- Licence consequence of the recommended route: none for distribution (nothing of ncurses is shipped; dynamic binding to an MIT-style library through FFM). `THIRD_PARTY_LICENSES` gets no entry; `JVM_BACKEND.md` names the runtime dependency.
- Windows: not applicable. PDCurses (public domain) could give Windows a `curses`, but CPython has none there, so it stays absent.
- The reference interpreters in WSL are uv's python-build-standalone builds, which link their own static ncurses: **unverified**, but if so the oracle and pyJVM use different ncurses builds on the same host, and `ncurses_version`, the `KEY_*` set and optional functions may differ. Mitigation: cases print nothing version-dependent, and remaining differences are documented. A distribution CPython linked against the system ncurses could serve as a cross-check, but Ubuntu 22.04's `/usr/bin/python3` is 3.10, which is not a lane (question d).

## 5. FFM binding design
New files: `PosixCurses.java` (FFM layer, ~700), `CursesModule.java` (module functions, constants, error formatting, ~800), `CursesWindow.java` (the `window` type, ~650), `CursesPanelModule.java` (~250).
- **Functions, macros, globals.** Most of curses's C API is real functions. What C code reaches through macros has function forms in ncurses: `getcury`/`getcurx`, `getbegy`/`getbegx`, `getmaxy`/`getmaxx`, `getpary`/`getparx`, `is_pad`, `is_keypad`, `wgetdelay`, and so on. Global variables are data symbols read through `SymbolLookup.find(...).reinterpret(4)` at each use, never cached: `LINES`, `COLS`, `COLORS`, `COLOR_PAIRS`, `ESCDELAY`, `TABSIZE`, `stdscr`, `curscr` (pointers), and `acs_map` (an array of `chtype`, indexed by character, the source of the `ACS_*` values). A reentrant ncurses build turns these into functions; detect by symbol presence and fail loudly if neither form exists. All of this is **unverified** against Ubuntu's library: spike S1.
- **Types** (ncurses ABI 6, LP64; assert what can be asserted in the spike): `chtype`, `attr_t`, `mmask_t` are 32-bit unsigned; `wchar_t` is 32-bit; `cchar_t` is `{attr_t attr; wchar_t chars[5]; int ext_color;}`, 28 bytes; `MEVENT` is `{short id; int x, y, z; mmask_t bstate;}`, 20 bytes. `WINDOW*` and `PANEL*` are opaque addresses.
- **Variadic calls:** `tparm(const char*, ...)` is variadic; CPython always passes nine integers. Declare it with `Linker.Option.firstVariadicArg(1)`.
- **Text.** With ncursesw, a `str` argument goes through the wide functions (`waddwstr`, `wadd_wch`, `wins_wstr`, `wget_wch`, `unget_wch`): Java `String` -> code points -> a 32-bit array. A `bytes` argument goes through the narrow functions. The window's `encoding` (default from `nl_langinfo(CODESET)`, called through FFM) is used where CPython encodes. ncursesw only renders UTF-8 when the C locale is the user's. The module does not set it on import (CPython does not either); instead `locale.setlocale` must reach libc on POSIX (a small change in `LocaleModule`, needed anyway for `nl_langinfo`), so that the documented idiom `locale.setlocale(locale.LC_ALL, '')` before `initscr()` works. Whether the JVM launcher has already called `setlocale(LC_ALL, "")` is **unverified** (spike S2).
- **Terminal and descriptors (N0).** `initscr()` uses C stdio's `stdin`/`stdout`, that is kernel descriptors 0 and 1, and writes with its own buffer. So: flush `sys.stdout`/`sys.stderr` (the Java-side buffers) before `initscr`, `endwin`, `putp` and `refresh`-family calls made while not in curses mode, or output interleaves wrongly. `setupterm(term=None, fd=-1)`: `fd` defaults to `sys.stdout.fileno()` (error `lost sys.stdout` when it has none); the number is passed straight to ncurses, which is only correct once N0 makes Python descriptors kernel descriptors. `getwin(file)`/`putwin(file)` need a C `FILE*`: CPython writes through a temporary file; do the same with libc `tmpfile`/`fread`/`fwrite`/`rewind`/`fclose` through FFM and copy to or from the Python file object.
- **Terminal modes and termios (N2).** `cbreak`, `raw`, `noecho`, `savetty`, `resetty`, `def_prog_mode` and friends change the tty through ncurses's own `tcsetattr` calls. No coupling with pyJVM's `termios` module is needed, but both then act on the same kernel tty state, which is the CPython situation too. `curses.wrapper` restores the terminal in a `finally`; in addition register one JVM shutdown hook (only after the first `initscr`) that calls `endwin()` if `isendwin()` is false, because a JVM that dies of an uncaught Java error would otherwise leave the user's terminal in raw mode. CPython has no such hook; it is invisible on normal exit.
- **Signals.** ncurses installs C handlers at `initscr`: SIGWINCH always, SIGINT/SIGTERM/SIGTSTP only where the disposition is still default (from knowledge of ncurses; **unverified**, spike S3). HotSpot owns SIGINT/SIGTERM unless `-Xrs`, so those stay with the JVM and pyJVM's `signal` module; SIGWINCH goes to ncurses, which is what makes `KEY_RESIZE` work. A Python `signal.signal(SIGWINCH, ...)` replaces it, as in CPython.
- **Blocking input (D5 of `native_modules_plan.md`).** `getch`, `getkey`, `get_wch` and `getstr` block in `read(2)`. CPython gets EINTR on Ctrl-C and raises KeyboardInterrupt; in the JVM the signal is taken on another thread, so the read is not interrupted. Rule: on the main thread, a blocking read is done in slices: remember `wgetdelay(win)`, loop `wtimeout(win, 50)` + `wgetch`, run `SignalModule.dispatchPending()` between slices, stop on input or when the window's own timeout has elapsed, restore the delay. `nodelay`, `halfdelay` and `timeout(ms)` semantics are preserved because the loop honours the saved delay. Use the same slice length N0 settles.

## 6. Threads, finalization, memory ownership
- ncurses keeps global state and is not thread-safe. CPython is protected by the GIL, which it releases only around the blocking input calls, `napms`, and a few refreshes. pyJVM: one global `ReentrantLock` around every curses and panel call; in the slice loop above it is released between slices, so another thread can draw while one waits for a key, as in CPython.
- `initscr` state flags (`setupterm` called, `initscr` called, `start_color` called) are module-level, as in C, and drive the "must call X first" errors.
- Windows: the Python object's state holds the `WINDOW*`, the encoding and a reference to the parent window's state (sub-windows and derived windows must be deleted before their parent; 3.14+ keeps the parent reachable from the child for this reason). `delwin` runs from a daemon `Cleaner` under the global lock, never for `stdscr`, and a parent's `delwin` is deferred until its children's states are freed (a child counter in the parent state, since the Cleaner gives no order). CPython deletes at refcount zero; here the memory lives until a collection, which has no visible effect on the screen.
- Panels: the state holds the `PANEL*`, the window object (kept alive by the panel, as in C) and the user pointer object; `del_panel` from the Cleaner under the lock. The bottom-to-top list is ncurses's own; `above()`/`below()` map `PANEL*` back to Python objects through a weak-valued map.
- Strings returned by ncurses (`tigetstr`, `keyname`, `longname`, `termname`, `unctrl`) point into library memory: copy at once. `tigetstr` returns `(char*)-1` for "not a string capability" and NULL for "absent": both give `None`, as in C.
- No upcalls anywhere in this module (ncurses has `use_screen`-style callbacks, but CPython does not expose them).

## 10. Risks and open questions
1. Nothing here was run. The surface comes from regular expressions over C sources and from knowledge of ncurses; step 0 must replace it with measurements before any code is sized against it.
2. Two owners of signals and of the tty in one process (HotSpot and ncurses). If spike S3 shows ncurses taking SIGINT or SIGTSTP from the JVM, set the dispositions back after `initscr` through `sigaction`.
3. Ctrl-C latency and idle wake-ups from the 50 ms slice loop; a JVM crash leaves the terminal raw (shutdown hook covers orderly exits only).
4. Output ordering between Java's `System.out` and ncurses's stdio buffer; N0 changes the engine under `sys.stdout`, so recheck after N0.
5. The reference interpreter may be linked with a different ncurses than the one pyJVM binds (section 4), which limits how exact the differential cases can be.
6. Struct layouts and global-variable symbols are hand-written for ncurses ABI 6 on x86-64; an ABI 5 or reentrant library must be refused at import, not half-supported.
7. GC-timed `delwin`: a program that creates thousands of short-lived windows holds native memory until a collection.

Questions for the owner:
- a. Bind the system ncurses (recommended, reasons in section 4) or vendor a private static build under the vendoring policy? The policy's wording ("large or security-sensitive items vendor a vetted library") would allow either reading; the plan needs the explicit choice.
- b. Is a JVM shutdown hook that calls `endwin()` acceptable, although CPython has none?
- c. `_pyrepl` (the interactive REPL) is the main consumer on 3.13/3.14: is an interactive pyJVM REPL wanted soon enough to pull step 1 (terminfo only) ahead of N0, or does all of curses wait behind N0 and N2?
- d. Should the Linux gate host gain a distribution CPython for a same-library cross-check, or are documented differences against the uv builds enough?

## Owner decisions (2026-11-16)
- Calling `endwin()` from a JVM shutdown hook is approved.
- Bind the system ncurses (`libncursesw.so.6`, `libtinfo.so.6`, `libpanelw.so.6`); do not vendor it (question a resolved).
